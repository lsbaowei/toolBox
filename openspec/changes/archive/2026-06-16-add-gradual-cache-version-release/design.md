## Context

当前工具库按功能目录组织，适合新增一个独立工具包来承载第三方缓存版本释放逻辑。业务侧会缓存第三方数据，缓存周期约 1-7 天；当第三方版本升级时，业务需要在较短窗口内逐步切换到新版本缓存 key，但不能立即全量刷新，避免对第三方接口造成突增流量。

该能力需要处理两个关键约束：已经释放到新版本的业务标识必须保持粘性；短时间出现多个新版本时，中间版本大概率是异常抖动，可以忽略并继续向第三方最新版本平滑释放。

## Goals / Non-Goals

**Goals:**

- 提供一个独立 Go 工具包，用于根据业务标识、第三方当前版本和释放配置，计算本次请求应使用的缓存版本。
- 支持固定释放窗口，例如 3 小时内从旧版本逐步释放到新版本。
- 支持粘性灰度：同一业务标识一旦使用某个新版本，后续请求不得回退到旧版本。
- 支持最新版本目标选择：`v1.1.1`、`v1.1.2`、`v1.1.3`、`v1.1.4` 连续出现时，保留释放节奏并最终释放到最新版本。
- 支持可注入时间源，便于单元测试和业务侧控制时间行为。

**Non-Goals:**

- 不负责直接请求第三方接口或管理第三方数据内容。
- 不提供分布式状态存储实现；首版以本地状态模型和可替换接口为边界。
- 不处理缓存系统本身的读写、过期和淘汰策略。
- 不保证跨进程天然一致性；多实例场景由调用方接入共享状态存储或在后续能力中扩展。

## Decisions

### 使用状态机管理版本释放

工具包维护当前稳定版本、正在释放的目标版本、释放阶段的起止时间，以及业务标识的粘性命中记录。相比仅用随机百分比实时计算，状态机可以清晰表达“稳定版本到最新版本”的释放过程，并为粘性灰度提供状态边界。

版本选择保留“每次仅比较稳定版本和第三方最新版本”的策略，然后按最新版本计算灰度比例。该方案实现更简单，也符合短时间连续版本大概率为异常抖动的判断；中间快速版本不单独释放，避免状态复杂度和总释放时间被异常版本拉长。

### 通过确定性分桶实现平滑释放

对业务标识和目标版本做稳定 hash，得到 `[0, 10000)` 的 bucket；再根据释放阶段已过去时间计算允许阈值。bucket 小于阈值时释放到目标版本，否则继续使用当前阶段的基准版本。

这种方式不需要随机状态，重启后同一业务标识在同一阶段会得到一致结果。已经释放的业务标识仍会记录到粘性状态，确保后续请求不会因时间或目标版本更新发生回退。

### 活跃释放目标跟随第三方最新版本

当输入版本不同于稳定版本时，若当前没有正在释放的版本，则以该版本开启释放阶段；若已有活跃释放阶段且又观察到更新版本，则将活跃目标更新为最新版本，但保留阶段起始时间和释放窗口，不为中间版本新增队列。

如果连续出现 `v1.1.1`、`v1.1.2`、`v1.1.3`、`v1.1.4`，工具包会保持从原稳定版本平滑释放的节奏，并把释放目标推进到 `v1.1.4`。释放窗口完成后，`v1.1.4` 成为新的稳定版本。

### API 保持小而可测试

首版建议提供 `Manager`、`Config`、`SelectVersion` 之类的核心 API。调用方传入业务标识、第三方当前版本和当前时间或时间源，返回应使用的缓存版本，以及可用于拼接缓存 key 的版本值。

状态存储先以内存实现为默认路径，同时把状态读写封装在内部结构中，避免业务代码依赖具体字段。后续如需接入 Redis、数据库或进程间共享状态，可在保持核心策略不变的前提下扩展。

## Risks / Trade-offs

- [Risk] 仅使用本地内存状态时，多进程或多实例之间的释放进度不一致。→ Mitigation：明确首版边界，核心状态结构保持可序列化，后续可扩展共享存储。
- [Risk] 业务标识粒度选择不当会影响释放均匀度。→ Mitigation：API 文档说明调用方应传入稳定且分布足够均匀的业务标识，例如用户 ID、租户 ID 或资源 ID。
- [Risk] 中间版本被忽略后，某些短暂版本不会形成独立缓存。→ Mitigation：该行为符合快速连续版本多为异常抖动的假设；工具包只保证最终释放到第三方最新版本。
- [Risk] 粘性记录长期增长可能带来内存压力。→ Mitigation：粘性状态只需覆盖活跃释放阶段，阶段完成后可清理不再需要的旧阶段记录。
