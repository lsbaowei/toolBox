## Why

当第三方接口发生大版本变更时，现有缓存会继续按原有过期时间命中旧数据，导致业务无法在可控时间内完成新版本数据刷新。直接全量切换又会在短时间内把大量请求打到第三方接口，存在打崩第三方服务的风险。

## What Changes

- 新增一个用于“缓存版本逐步释放”的工具包，支持根据第三方返回的版本号生成业务可用的缓存版本。
- 当检测到新版本时，在配置的释放周期内逐步将业务请求从旧版本释放到新版本，避免瞬时全量刷新。
- 对已经命中新版本释放结果的业务标识保持粘性，确保后续请求继续使用已释放的新版本。
- 当短时间内连续出现多个新版本时，以最新版本作为释放目标，中间快速版本视为异常抖动可忽略。
- 提供可测试、可复用的 API，便于不同业务场景接入自定义业务标识、版本来源、释放时长和时间源。

## Capabilities

### New Capabilities
- `gradual-cache-version-release`: 定义第三方版本变更时缓存版本的渐进释放、粘性灰度和最新版本目标选择行为。

### Modified Capabilities
- 无。

## Impact

- 新增工具包目录，用于承载缓存版本逐步释放逻辑及其单元测试。
- 可能新增面向业务调用方的 Go API，包括版本状态管理、释放策略计算、缓存 key 版本选择等能力。
- 不引入外部服务依赖；默认实现应可通过内存状态和可注入时间源完成测试。
