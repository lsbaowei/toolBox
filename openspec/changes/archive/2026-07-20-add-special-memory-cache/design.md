## Context

`utils_cache_memory` 目前只有需求说明，尚无实现。目标场景需要在单进程内并发保存 `[]byte`，同时记录绝对过期时间；缓存位于高频路径，因此数据封装与读取应尽量减少复制和临时对象。仓库使用 Go 1.19，设计不能依赖更高版本新增的 `sync.Map` API。

## Goals / Non-Goals

**Goals:**

- 提供零值可用、并发安全的缓存类型，所有实例共享一个进程级 `sync.Map`。
- 用单个 `[]byte` 同时承载过期时间和业务数据，固定头部为 8 字节 Unix 秒级时间戳。
- 支持常用的存取、删除、遍历与过期清理操作。
- 明确切片所有权，在安全边界内减少复制，并以测试和 benchmark 验证行为及分配情况。

**Non-Goals:**

- 不提供跨进程共享、持久化、容量限制、LRU/LFU 淘汰或分布式一致性。
- 不启动后台 goroutine 定时清理，也不承诺过期数据在读取前已从内存移除。
- 不提供泛型序列化；调用方负责将业务值编码为 `[]byte`。
- 不保证多个缓存实例之间的数据隔离。

## Decisions

### 使用零尺寸 `Cache` 类型和包级 `sync.Map`

定义零值可用的 `Cache`，内部操作统一委托给包级 `sync.Map`，因此可直接声明 `var cache utils_cache_memory.Cache`，且不同实例访问同一缓存空间。这符合“全局一个 `sync.Map`”的约束，也避免每次初始化分配状态。

备选方案是让每个 `Cache` 持有自己的 `sync.Map`。该方案隔离性更好，但与全局共享要求不符，且会改变不同实例间可见性。

### 条目采用 8 字节头部加原始数据

`Set` 分配一个长度为 `8 + len(value)` 的切片，使用固定字节序把 `int64` Unix 时间戳写入前 8 字节，并将业务数据复制到剩余区域。`Get` 解码头部后直接返回业务数据子切片，不再复制。

必须在 `Set` 时复制业务数据，否则调用方后续修改或复用输入切片会破坏缓存内容。作为低复制设计的代价，`Get` 返回的切片与缓存条目共享底层数组；API 文档将要求调用方只读使用，如需修改必须自行复制。

备选方案是分别保存时间戳和数据结构体，语义更直观，但不符合指定的连续字节布局。每次 `Get` 再复制数据虽然隔离性更强，但会增加高频读取的分配和 GC 压力。

### 使用绝对过期时间并约定零值不过期

正数 `expireAt` 表示 Unix 秒级绝对过期时间；当 `expireAt <= now` 时条目过期。`expireAt == 0` 表示永不过期，负数输入视为无效并拒绝写入。时间判断使用可替换的包内时间函数，以便单元测试稳定覆盖边界。

`Get` 发现条目过期时返回原过期时间和业务数据，同时返回未命中状态，方便调用方判断或降级使用，但不自动删除数据。所有存取操作直接使用 `sync.Map` 提供的并发安全能力，不额外引入互斥锁。调用方根据业务需要显式调用 `Delete` 或 `DeleteExpired` 清理数据；`DeleteExpired` 接受与 `sync.Map.Range` 一致的弱一致性，在清理与相同 key 并发写入时允许删除新值。

备选方案是使用相对 TTL，但需求明确要求传入过期时间戳。后台定时清理会引入 goroutine 生命周期和扫描频率配置，因此不采用。

### 提供与需求匹配的最小并发 API

首版提供 `Set`、`Get`、`Delete`、`LoadAndDelete`、`Range` 和 `DeleteExpired`。key 使用 `any` 并遵循 `sync.Map` 对可比较 key 的要求。`Range` 仅回调有效条目并携带 key、过期时间和数据；`DeleteExpired` 接收当前 Unix 时间，便于调用方按需批量清理并获得删除数量。

不在首版实现 `LoadOrStore`，因为其“加载或写入”语义还需同时定义过期替换和输入切片所有权，容易扩大 API 面。Go 1.20 之后的 `Swap`、`CompareAndSwap`、`CompareAndDelete` 以及 Go 1.23 的 `Clear` 也不纳入 Go 1.19 兼容 API。

## Risks / Trade-offs

- [返回切片可被调用方修改，可能破坏缓存内容] → 在 API 和 README 中声明返回值只读，并用测试记录该零复制契约。
- [全局缓存导致不同实例或测试之间 key 冲突] → 明确全局共享语义，测试使用唯一 key 并在结束时删除。
- [惰性过期使未访问的过期条目继续占用内存] → 提供 `DeleteExpired`，由业务按自身负载决定清理时机。
- [遍历期间并发更新导致视图不一致] → 继承 `sync.Map.Range` 的弱一致性语义，不承诺快照。
- [过期清理与并发覆盖存在竞争，可能删除同 key 的新值] → 明确 `DeleteExpired` 的弱一致性和调用方管理责任，由业务选择低写入时段或可容忍重写的场景执行清理。
