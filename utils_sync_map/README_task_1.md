你的想法本质上是：**固定 Bucket 数量，通过调整单个 Bucket 覆盖的时间范围，控制索引管理成本与清理粒度。**

但这里有一个关键区别：Bucket 覆盖范围越大，单个 Bucket 内的 KEY 越多，清理时可能需要扫描更多数据。

## **1. 两种配置对比**

假设 Bucket 数量固定为 60 个：

| 配置   | Bucket 数量 | 单个 Bucket 时间范围 | 总覆盖时间 |
| ---- | --------- | -------------- | ----- |
| 方案 A | 60        | 6 分钟           | 6 小时  |
| 方案 B | 60        | 1 分钟           | 1 小时  |

这里的时间范围是分桶粒度，不是 TTL 上限。

**方案 A：6 小时覆盖**

每个格子代表一个 6 分钟 Bucket，共 60 个。

**方案 B：1 小时覆盖**

每个格子代表一个 1 分钟 Bucket，共 60 个。

| 维度           | 6 小时 | 1 小时 |
| ------------ | ---- | ---- |
| Bucket 数量    | 60   | 60   |
| 索引管理成本       | 较低   | 较低   |
| 单 Bucket 数据量 | 较大   | 较小   |
| 清理粒度         | 较粗   | 较细   |
| 单次清理工作量      | 可能较大 | 相对较小 |
| TTL 更新迁移     | 可能较少 | 可能较多 |

## **2. 我更推荐动态配置时间粒度**

不一定非要固定 1 分钟或者 6 分钟。

可以把 Bucket 数量固定为 60，时间范围作为配置：

```
type CacheConfig struct {
    BucketCount    int
    BucketDuration time.Duration
}
```

例如：

```
// 惰性清理
BucketCount:    60,
BucketDuration: 6 * time.Minute,

// 相对积极的清理
BucketCount:    60,
BucketDuration: 1 * time.Minute,
```

Bucket ID：

```
func (c *Cache) getBucketID(expireAt int64) int64 {
    return expireAt / int64(c.bucketDuration)
}
```

注意：如果采用固定 60 个环形 Bucket，还必须保存完整的绝对时间槽编号，不能仅使用 `% 60` 判断 Bucket 是否属于当前轮次。

## **3. 但有一个更重要的问题：你的清理周期是 1～3 小时**

如果你每 2 小时才执行一次 Cleanup，那么：

- 1 分钟 Bucket 并不意味着 1 分钟清理一次。
- 6 分钟 Bucket 也不意味着 6 分钟清理一次。
- 两者实际清理延迟都主要由 2 小时的 Cleanup 周期决定。

因此，Bucket 粒度不应该单纯追求精细。

**如果业务允许过期数据在内存中多保留 1～3 小时，我倾向于 6 分钟粒度。**

它能减少 Bucket 管理数量之外的实际管理开销吗？不会减少 Bucket 数量，但可以减少 KEY 在相邻 Bucket 之间迁移的频率。

## **4. 我的最终建议**

推荐第一版

| 配置         | 建议            |
| ---------- | ------------- |
| Bucket 数量  | 60            |
| Bucket 粒度  | 6 分钟          |
| 时间覆盖       | 6 小时          |
| Cleanup 周期 | 2 小时          |
| 清理方式       | 后台遍历到期 Bucket |
| Entry      | 不可变指针         |

不过还要注意一个边界条件：

如果 TTL 超过 6 小时，不能直接把它放进 60 个 Bucket 后假设一定能在正确轮次清理。应该使用绝对时间槽编号识别轮次，或者让 Bucket 管理结构能够容纳未来时间槽。

**我的观点：对于你的读多写少场景，6 分钟比 1 分钟更值得先尝试。** 真正需要 Benchmark 的不是 Bucket 数量，而是单 Bucket 的平均 KEY 数量、TTL 更新迁移成本和 Cleanup 峰值耗时。
